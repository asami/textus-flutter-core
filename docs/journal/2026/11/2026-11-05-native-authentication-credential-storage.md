# Internal native authentication credential storage prerequisite

Date: 2026-11-05. Task: ESA610-NATIVE-CREDENTIAL-STORAGE-001, same original active whole Phase 6.10 and explicit Core common-authentication purpose. This records bounded implementation scope, not validation, native execution, Step/Phase acceptance or a release.

The accepted authentication client assigns protected session storage to Core. The new internal [storage specification](../../../spec/native-authentication-credential-storage.md) implements only that prerequisite: opaque bytes with exact local profile slots, random storage revisions, atomic CAS, conditional revision removal, explicit unconditional slot recovery/clear and handle retirement/drain. It has no root export or production App/Framework consumer, login verifier, session issuer, server route/JSON assumption, TTL, automatic restoration or network work.

Android uses a separate no-backup SQLite database and exact per-profile AndroidKeyStore AES-GCM alias/AAD, with comparison/decryption/mutation and key cleanup under one write transaction. Corrupt/incompatible data and lost keys fail closed without reset or replacement. iOS uses default-group, non-synchronizable data-protection Keychain with AfterFirstUnlockThisDeviceOnly accessibility and one process-wide comparison/mutation lock. Both engines keep IO off main, retire before queue barriers, drain issued work, withdraw retired values/errors and suppress detached replies. Close does not remove persistent data or roll back an issued write. Diagnostics expose only safe categories.

Meaningful Dart protocol, synthetic JCE and injected Swift Keychain/lifetime specifications accompany the implementation. The separate App opt-in target uses synthetic reserved profiles, refuses pre-existing data, checks actual native storage/CAS/fresh-handle behavior, and conditionally removes only revisions it created. Its qualification procedure requires data-preserving signed updates/restoration; no real token, account, book/media/settings operation, cloud transfer or result oracle is introduced.

No test/analyzer/formatter/build/native execution was performed by the implementation worker. Parent-selected focused validation, signed Android/iOS artifacts, actual available physical-device probes, normal App/data restoration and one independent protected-focused conformance review remain required; unavailable devices remain pending. Host fakes, fresh-handle reopen and compiled artifacts prove neither new-process persistence nor genuine provider/server authentication.

The required future Core backend still needs accepted server HTTP specimens and normalized codec, provider-account binding, refresh/logout and account-safe queue ownership. It must check current operation before persistence, conditionally remove its own late-write revision on cancellation and drain before publication; store.close is not logout/cancellation rollback. Existing client authority and all original whole-Phase gates remain unchanged.
